Why that number in the header is the whole point

The viewer rebuilds the arm from the same joint frames the generated URDF declares, then checks its own tool-centre position against the analytic forward kinematics Python exported for every one of the 460 frames. The figure in the status pill is the live worst-case disagreement, recomputed in your browser on load. If this page had drifted from the simulation it would say so here rather than quietly look plausible.

Straight answers about what has actually been measured and what has not.

Real and measured

verified
  • The viewer's kinematics agree with the simulation's to picometres across all 460 frames.
  • Closed-form IK round-trips against forward kinematics to 3×10⁻¹⁶ m.
  • 120 / 120 tubes into the correct rack across 20 seeded trials.
  • Detection error ≈1 mm against an 18 mm grasp tolerance.
  • 291 tests, green on Python 3.10 and 3.11 in CI, with no GPU and no hardware.

Not yet proven

needs hardware
  • No physical arm has ever run this. The SO-101 driver is written against LeRobot's real API and covered by 33 tests against fakes — the serial link itself is untested.
  • Grasping in simulation is constraint-based, not friction-based. Real tubes slip; these do not.
  • Colour thresholds are tuned to the renderer. Real lighting will need retuning.
  • The ACT policy pipeline runs end to end but was never trained properly — that was out of scope, not a result.

The seed pins the layout, so you get the run on the overview, exactly.
